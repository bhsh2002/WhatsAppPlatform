# Landing, session, and responsive workspace update

This release aligns the public landing page, authentication screens, and the
authenticated workspace around one visual system while preserving the existing
operational workflows.

## User-visible changes

- The landing page now uses shared, organization-neutral language. Commerce,
  services, institutions, and digital products remain represented as explicit
  use cases instead of defining the shared message.
- The hero example follows a generic service request rather than a sales-only
  scenario.
- Credit notes describe platform usage only and do not reference Meta pricing.
- Authenticated users can open `/` and stay on the landing page. Entry buttons
  lead them directly to their admin or tenant workspace.
- Login, the mobile header, sidebar, and dashboard cards use the same warm
  paper, green, coral, typography, and asymmetric shape language as the landing
  page.
- Mobile tables scroll horizontally while keeping useful column widths. Long
  prose wraps at normal word boundaries; phone numbers, action labels, status
  chips, and priority values no longer break character by character.
- Facebook Insights date controls stack on narrow screens instead of clipping
  the action button.

## Session contract

`GET /auth/session` is a public browser bootstrap endpoint:

- No valid session: HTTP 200 with
  `{ "authenticated": false, "user": null, "tenant": null }`.
- Valid session: HTTP 200 with `authenticated: true` and the same allow-listed
  user and tenant profile fields returned by the protected `/auth/me` route.
- Expired, invalid, or revoked credentials are treated as an anonymous browser
  state. Protected application routes continue to enforce authentication and
  authorization normally.

This avoids an expected `401` request on public pages without weakening any
protected endpoint.

## Deployment impact

- Rebuild both the server and client images.
- No database migration is added; the schema remains at 39 migrations.
- No new environment variable is required.
- Existing `Secure`, `HttpOnly` session cookies scoped to `/api` remain valid.

## Production smoke checks

After deploying, verify the existing readiness and public surfaces:

```bash
curl -fsS https://wa.savana.ly/api/health
curl -fsS https://wa.savana.ly/api/auth/session
curl -sS -o /dev/null -w 'frontend=%{http_code}\n' https://wa.savana.ly/
```

Then sign in, open `https://wa.savana.ly/`, confirm that the landing page remains
visible, and use its workspace button to return to the correct dashboard.
